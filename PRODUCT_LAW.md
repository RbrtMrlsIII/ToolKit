# PRODUCT_LAW.md — Universal AGENT Toolkit Product Law

> **Human authority is highest.** `PRODUCT_LAW.md` is the canonical reconstruction of the user's approved vision, purpose, invariants, boundaries, and non-negotiable outcomes for this Toolkit. It does not replace user authority, and it may not be silently rewritten by an Agent, skill, tool, provider, workspace, or implementation detail.

## 0. Authority chain

```text
USER COMMAND / VISION
        ↓
consult applicable Agents / tools
        ↓
USER APPROVAL for material direction
        ↓
reconstruct PRODUCT_LAW.md
        ↓
MASTERPLAN.md checklist / current slice
        ↓
skills + applicable knowledge
        ↓
O-R-U-C-A-V-E-A execution discipline
        ↓
action / implementation
        ↓
validation
        ↓
evidence + complete log
        ↓
endorsement
        ↓
PRODUCT-KNOWLEDGE.md growth
        ↺ future skill / governance evolution
```

The Toolkit exists to make this chain reliable, inspectable, recoverable, and reusable across consuming projects.

## 1. Product identity

Universal AGENT Toolkit is a reusable operating substrate for AI-assisted projects. It provides operating mechanisms, skills, governance patterns, continuity, knowledge discipline, project adaptation, and scale adaptation.

It is not a consuming project's Product Law. It does not own a consuming project's domain semantics, provider decisions, credentials, production state, or authorization policy.

## 2. Non-negotiable boundaries

- User authority is above every Agent output.
- Product Law defines what the project is and what must remain true.
- POLICY defines execution/governance rules but must not redefine product meaning.
- MASTERPLAN defines the approved execution map and slice/checklist order.
- Skills instruct how authorized work is performed; a skill never grants authorization.
- Tools/capabilities expose mechanisms; permission and authorization determine whether they may be controlled.
- Evidence proves what happened; evidence does not become authority merely because it exists.
- Historical material remains historical unless explicitly promoted through the authority chain.
- Consumer-specific knowledge does not become universal knowledge merely because it was useful once.

## 3. Universal core vs consumer extension

Every Toolkit artifact, skill, pattern, or rule belongs to one scope class:

| Scope | Meaning | Default destination |
|---|---|---|
| `UNIVERSAL` | Reusable across projects and fields | Toolkit core |
| `ADAPTABLE` | Universal mechanism with project/field parameters | Toolkit core + consumer adapter |
| `CONSUMER-SPECIFIC` | Belongs to one consuming project's law/domain/runtime | Consumer project |
| `EPHEMERAL` | Session/task/finding context only | Working state |
| `HISTORICAL` | Preserved evidence/evolution record | History/archive |
| `CANDIDATE` | Proposed upstream knowledge awaiting validation/endorsement | Candidate queue |
| `ENDORSED` | Validated reusable knowledge accepted as universal | Toolkit knowledge/skill surface |

No artifact may silently cross scope classes.

## 4. Responsibility-first architecture

Toolkit is organized around responsibilities, not Agent identities.

```text
Responsibility Unit
  = objective
  + scope
  + required skills
  + required knowledge
  + verification
  + authority boundary
  + outputs
  + dependencies
```

```text
Seat
  = responsibility units
  + workspace governance
  + project adaptation
  + skill bundle
  + execution capacity
```

```text
Agent
  = currently assigned responsibility units
```

Agent count therefore changes allocation, not the underlying universal skill definitions.

## 5. Execution baseline and skill growth

A **baseline freeze** is a deliberate point where a validated execution path, boundary, or recovery pattern becomes stable enough to reuse.

Baseline freezes create skill demand:

```text
validated baseline
      ↓
repeatable procedure discovered
      ↓
skill coverage review
      ↓
new skill / skill extension / anti-pattern / validator
      ↓
scope + dependencies + verification recorded
      ↓
future slices consume the smallest sufficient bundle
```

Skills are therefore **living infrastructure**, not a static catalog. The Toolkit may add, refine, split, deprecate, or retire skills as validated execution baselines multiply. Skill growth must remain subordinate to Product Law and governed by scope, verification, and knowledge evidence.

A growing skill count is healthy only when it increases reusable execution precision without multiplying authority or duplicating knowledge unnecessarily.

## 7. Change integrity principle

Canonical structure is part of project knowledge. Deleting unrelated canonical content is a semantic failure even when the requested new statement is present.

### Canonical Structure Preservation

When updating a canonical document:

1. Preserve all unrelated canonical content.
2. Change only the authorized semantic scope.
3. Detect unexpected deletions.
4. Detect unexpected section loss.
5. Verify structural integrity before merge.
6. Treat unexplained canonical deletion as fail-closed.

A change claiming to update one frontier but removing unrelated canonical sections is a governance failure, not a cosmetic diff.

## 8. Bidirectional consistency

Relationships must be testable from both directions where the architecture claims them:

```text
documentation ↔ implementation/evidence
skill ↔ scope
scope ↔ applicable skill
claim ↔ evidence
field ↔ responsibility
baseline ↔ skill coverage
```

A one-sided index is not sufficient proof of consistency.

## 9. Knowledge promotion rule

```text
consumer finding
      ↓
observed + recorded
      ↓
validated by evidence
      ↓
generalization review
      ├── reusable → Toolkit CANDIDATE
      └── product-specific → stays downstream
      ↓

      ↓
ENDORSED Toolkit pattern / anti-pattern / skill / governance rule
```

No automatic downstream overwrite follows Toolkit promotion.

## 10. Instruction vs authorization

```text
Skill                → HOW
POLICY / workspace   → WHETHER
Permission            → WHETHER THE AGENT MAY ACT
PRODUCT_LAW          → WHAT IS TRUE
MASTERPLAN            → WHAT APPROVED SLICE IS NEXT
Evidence              → WHAT WAS PROVEN
```

A skill cannot authorize repository mutation, deployment, production access, billing changes, credential handling, or other privileged operations by itself.

## 11. Scope of the universal roadmap

The Toolkit roadmap is intentionally staged:

```text

D  Knowledge Promotion / Generalization
E  Canonical Change Integrity
F  Bidirectional Evidence / Claim Validation

```

Capability growth and discipline growth must be tracked together.

## 12. Definition of a healthy Toolkit change

A healthy change can answer:

- What did the user authorize or require?
- What Product Law does the change serve?
- Which current Masterplan slice owns the work?
- Which skills and knowledge are required?
- Which canonical structures must remain synchronized?
- What authority and permissions permit the action?
- What evidence proves the result?
- What reusable knowledge was learned?
- What changed in future execution capability or governance discipline?

Failure to answer these questions creates an investigation or a blocked change, not a guess.
